# Doors v0.0.10: release candidate and hardware gate (2026-09-16)

The release record for Doors 0.0.10, the first release under the Doors name
(docs/releases/v0.0.10.md). The release candidate is `9f9c802`, the release
commit on `release/v0.0.10`, built once from fresh clones, flashed to the
development card and run through one gate on unit A. A second candidate that
tried to work around the boot-splash finding was built, validated and
rejected; it is recorded below and is not part of the release.

**Verdict: PASS, with a known boot-splash limitation** (product owner,
2026-09-16). Every host, build and image gate passed, the card was written and
read back, every remote hardware check passed, and the operator's panel pass
(UI, rotation, touch, safe area, icons, apps) passed. The vendor U-Boot's
first splash render is intermittently black, on cold boots and warm reboots
alike, while the boot into Doors is unaffected; it is classified as a known
vendor U-Boot/display-init limitation and ships documented (section
"Boot splash: known vendor limitation").

Remote results are VERIFIED on unit A over the serial console (COM9,
115200): the bench had no network to the unit, so no step used SSH. What the
panel showed is the operator's observation. Board time is UTC and reads 1970,
because nothing could reach an NTP server. Serial captures, the gate scripts
and the flash logs are in `out/doors-0.0.10-rc-9f9c802/` (`hwgate-unitA/`) and
`out/doors-0.0.10-rc-236a142/` (ignored).

## Boot splash: known vendor limitation

**Classification (product owner, 2026-09-16):** a known vendor U-Boot /
display-init limitation. The splash file, its conversion and the image are
not the cause; the boot into Doors is not affected.

Every boot of `9f9c802` whose panel the operator watched from power-on:

| Boot | USB power off before it | Base | Splash (operator) |
| --- | --- | --- | --- |
| First power-on after the flash (row A) | several minutes (card in the host reader) | attached | **seen** |
| Row D, first cycle | about 10 s | detached | **black** until Doors |
| Row D, second cycle | about 10 s | attached | **black** until Doors |
| Splash test (below) | 367 s | detached | **seen**, at +30 s and at +2 min |
| Operator's own cold boot after the splash test | about 60 s | detached | **black** until Doors |

Warm reboots of `9f9c802` were not watched. On 2026-09-15 the same boot path
gave no splash after a warm `reboot` (DOORS_GRAPHICS_GATE.md), and the rejected
candidate below showed it on three warm reboots.

**The splash test.** One power cycle with the base detached and USB power
removed for 367 s, captured from the first U-Boot line and held at the U-Boot
prompt with autoboot stopped, so nothing could replace the splash. U-Boot:
`2799104 bytes read`, `RM69A10 direct XRGB8888 logo.xrgb full-screen OSD4`.
Panel GPIO bank `02400000` (as on 2026-09-15); DSI `PHY_STATUS`
(`0x908500b0`) `0x1529`; the operator saw the splash at +30 s. The vendor
`k230_logo` was run again at +60 s; afterwards `PHY_STATUS` read `0x15bb` while
the operator still saw the splash at +2 min. Then `boot`: the kernel preserved
the splash (`preserving boot splash`, `skip DRM fbdev setup`), Doors took the
panel at 17.98 s (`prepare: sending init commands`), and the per-boot check
passed (27 ok).

**Observed.**

- The splash sometimes appears on a cold boot, and sometimes stays black on a
  true cold boot (about 60 s without USB power, base detached; the base has no
  battery).
- A warm reboot can show the same behaviour (2026-09-15).
- Both `k230_logo` invocations can execute and load 2,799,104 bytes while the
  physical panel stays black (the rejected candidate, boot B5 below). The
  U-Boot and kernel console output of a black boot is identical to that of a
  boot with the splash, so the console does not show the failure.
- Keyboard-base presence does not explain it: seen and black both with the
  base detached, black with it attached.
- The boot into Doors is otherwise successful every time: rotation, touch and
  services as in rows A-E.
- The image is not the cause: the bootloader region before partition 1 and
  every boot-partition file (`logo.xrgb`, `logo.yuv`, `Image`, all device
  trees) are byte-identical to `e999ab1`, whose splash was verified from
  power-on on 2026-09-15, apart from 7 header bytes of
  `fw_jump_add_uboot_head.bin` (timestamp and CRC).
- A single read of `PHY_STATUS` at the U-Boot prompt does not decide lit or
  black: `0x1529` lit, `0x15bb` black (2026-09-15), `0x15bb` lit (after the
  second `k230_logo` in the splash test).

**Unknown.**

- The root cause inside the vendor panel power, reset and DSI bring-up.
- A deterministic retry point that fixes it.

This is not attributed to power-off time, capacitor discharge or keyboard-base
back-feed; an earlier reading of the short-off boots as the cause was withdrawn
when a cold boot after about 60 s came back black. Investigating the vendor
bring-up is post-v0.0.10 work (docs/ROADMAP.md).

## Harness notes

- The first automatic post-hand-over check ended early: its end marker also
  occurred in the echoed command line, which the console wrapped. The check
  ran on the unit unobserved; it was run again at once (`handover-2`, row B),
  and every later marker was chosen so that it cannot occur in a command.
- The watcher armed for row D recorded nothing: when USB power was removed the
  CH342 port disappeared, and the open .NET `SerialPort` handle neither failed
  nor saw it return. Later watchers poll the system's port list instead.
- On a cold power-up the CH342 port can come back after U-Boot has started, so
  a capture may miss the first draw (RC2 boots B1 and B5); the second draw and
  everything after it are always captured.
- The RC2 cold-boot watcher stopped when B5's port vanished before its login
  check, so B6 booted unobserved; the watcher was re-armed within a minute.
- None of these affected the unit or any result recorded above.

## Known issues carried into v0.0.10

The release notes list the ones that matter to a user; docs/KNOWN_ISSUES.md is
the full list. The ones that bound what this release claims:

- Attaching or removing the keyboard base on a powered unit is **not** a
  verified or supported operation; this gate changed the base only with the
  power off and USB power removed.
- The boot splash is intermittently black, cold and warm (known vendor
  limitation above).
- App screens keep their portrait layouts in landscape (ROADMAP, "Landscape
  app adaptation").

Doors' own licence is undecided, so redistribution is not authorised
(docs/LICENSING.md, open items 1 and 8). This release is a tag in the private
repository, not a publication.

## Upgrade and rollback

As in docs/releases/v0.0.10.md: flash for an upgrade from v0.0.9 (data on the
card is replaced), hand the panel over with the two `/etc/default` files, and
flash the v0.0.9 image to go back. This gate exercised the flash and the
hand-over; the bench `deploy.sh` migration and `rollback_phase3.sh` were
exercised by the Phase 3 gate (DOORS_PHASE3_GATE.md, steps A and E) and are
unchanged in this release.
