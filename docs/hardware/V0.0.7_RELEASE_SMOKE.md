# PocketOS v0.0.7: release image and hardware smoke test (2026-09-10)

The nine-step run defined in V0.0.7_PRE_RELEASE_CHECKPOINT.md, carried out end
to end on unit A the same day the checkpoint was written.

**Verdict: PASS.** The image built in one attempt from a clean clone, wrote and
byte-compared to a card, cold-booted, and reproduced every behaviour the four
bench sheets had established - this time from a flashed rootfs rather than
binaries copied onto a 0.0.6 card. Both destructive actions were carried out
from the panel, and the LoRa probe returned VERIFIED.

Three things came out of it that are worth more than the pass: what a fresh
image does that a bench deployment never did, why the LoRa probe needed a power
cycle, and one criterion in the checkpoint that was written from the wrong
starting state.

### Rootfs against v0.0.6

8368 -> 8370 files; 933 symlinks and 1281 directories unchanged. Read out of
both images with `debugfs`, no mounting and no root.

- **Added (2):** `/etc/init.d/S50sysd`, `/usr/sbin/sysd`.
- **Removed:** none.
- **Changed (10):** `/etc/pocketos-release`; the four PocketOS binaries
  `usr/bin/pocketos-shell`, `usr/bin/pos`, `usr/bin/pos-supervise`,
  `usr/sbin/radiod`; and the documented non-reproducible vendor set -
  `/etc/version/release_version` and four launcher binaries under
  `/root/app/k230_phone_ui`, rebuilt by every apply.

Nothing else. That is the whole of v0.0.7 on disk: one service, its init
script, and the binaries that carry the new code.

A first pass at this diff reported four extra changed files
(`setuptools/.../Lorem ipsum.txt`, `command/launcher manifest.xml`,
`script (dev).tmpl`, `openal/hrtf/Default HRTF.mhr`). All four are byte
identical in both images; the comparison had split filenames containing spaces
on whitespace. Recorded because the corrected method - keying on a fixed column
rather than on fields - is what the next release diff should use.

## Flash

Target: a 15,634,268,160-byte USB card, a LILYGO reuse supplied by the
operator, erase authorised. Its size alone proves it is none of the evidence
cards, every one of which was written on the 62.9 GB card, so the writer's size
gate was retargeted to this card and **no other gate was changed**. Before the
write it carried bootloader region `57CDE803...5680`, prefix
`FAADEE0C...0078` - not any PocketOS build, the factory image.

| | |
| --- | --- |
| Gates | source hash and size, nine identity gates, and the re-gate after the partition wipe: all PASS |
| Write | 763,363,328 bytes in 150.9 s (4.8 MB/s), **0 drops** |
| Byte compare | full range compared; **4 differing bytes, range `440..443` only** |
| Verdict | FLASH PASS |

The writer's own last line reads `RESULT: FLASH FAIL`, and that is expected: it
compares the whole-image hash, which cannot match once Windows stamps the MBR
disk identifier into bytes 440..443. Adjudicating that is exactly what the
byte-compare wrapper exists for, and it is the wrapper's verdict that counts.
Anyone reading the raw writer log in isolation will be misled; the two must be
read together.

## What a fresh image does that a bench deployment never did

**It boots to the vendor launcher.** `/etc/default/k230_phone_ui` and
`/etc/default/pocketos-shell` do not exist in the image at all; the defaults
compiled into the init scripts are launcher `ENABLE=1` and shell `ENABLE=0`.
That is the documented v0.0.7 state - the shell is installed, not yet the
default owner of the panel - and it is invisible from a bench deployment,
because the 0.0.6 card had those files already flipped in its rootfs.

**It has no `authorized_keys` and a new SSH host key.** Both are unavoidable
consequences of a fresh rootfs and both stopped the run until the operator
restored the key over the serial console and read the new ED25519 fingerprint
(`SHA256:TC7dhTt2GcGokEL5FeXQw4l8gadH2Q7yNBx38BVRp7Q`) off the physical
console. `known_hosts` was only rewritten after the key offered over the
network was compared against that reading and matched. Anyone reflashing should
expect this and have the serial console attached before they start.

### 5. Cold boot

`/etc/pocketos-release` reads `0.0.7` with `BUILD_ID=4ab5a55`; `pos 0.0.7
(build 4ab5a55)`. Supervised services `running=1`, `crashloop=0`,
`restarts=0`, pid-identity deltas **0 s**, no crash-loop markers, no temp state
files, `S50sysd` present in `/etc/init.d`.

**One checkpoint criterion was wrong, not the image.** It required "all three
services running" at first boot. On a fresh image only sysd and radiod are
supervised, because `S90pocketos-shell` correctly refuses to start while the
launcher owns the panel - so the honest reading of first boot is 2/2, and
`system.status` reported exactly those two. The criterion had been written from
the deployed state, where the switch was already flipped. After flipping it and
rebooting, 3/3.

### 6. The screen, on the image

Values were compared through `system.status` and `system.info` rather than read
off the glass, which is the right division of labour: the rendering was already
validated on the bench and is unit-tested, and what this run had to prove is
that the image reproduces it. Storage read `131 MB free of 574 MB` and `46 MB
free of 69 MB` against `avail_bytes` 137850880 / 48829440; memory, uptime and
clock agreed; the four interfaces include `sit0` with the four-octet MAC
`00:00:00:00`, filtered out of the human view.

Confirmed at the panel, because none of it is observable over SSH:

| Check | Observed |
| --- | --- |
| Screen opens, indicator | `System`, `LIVE` |
| Layout and scrolling | smooth top to bottom, no clipping, no overlap |
| Interface filter | `1 interface hidden` present under the Network panel |
| `S60radiod stop` | `radiod` row `STOPPED`; Radio chip **grey**, `--` |
| `S60radiod start` | `radiod` row `RUNNING`; Radio chip **blue**, `RX` |
| Restart dialog | title, body and buttons correct, action accented |

The two rows in bold are the v0.0.7 pre-release UI fixes (`ab65d03`,
`dbba4a0`) reaching a flashed image for the first time. The shell was never
restarted through any of it (pid 273, `restarts=0`).

### 7. Reboot and power off, from the panel

```
17:01:07.539Z sysd INFO  reboot accepted, acting in 200 ms
17:01:07.739Z sysd INFO  reboot: running /sbin/reboot
17:02:45.267Z sysd INFO  poweroff accepted, acting in 200 ms
17:02:45.468Z sysd INFO  poweroff: running /sbin/poweroff
```

**200 ms** between reply and command in both cases, and three clean supervisor
exits each time - a line written only on a supervisor's own shutdown path, so
nothing was force-killed. After the reboot: fresh `/run`, pids 235/253/274,
`restarts=0`, deltas 0. After the power off: down confirmed from this end (100 %
loss over 20 pings, `No route to host`), USB out for about 30 seconds, then a
normal boot to PocketOS with the SoC at **46.2 °C** against the ~48.5 °C it had
been running at - the cold-start signature, as in the block 2c smoke.

### 9. The LoRa probe, and why it needed a power cycle

Run twice, and the pair is the interesting part:

| Run | Chip status byte | Register window | Verdict |
| --- | --- | --- | --- |
| after the warm reboot | `a2` | `a2 a2 a2 a2 24 b4` | no VERIFIED line |
| after the USB power cycle | `aa` | `aa aa aa aa 14 24` | **VERIFIED**, exit 0 |

This reproduces the v0.0.6 conclusion from a clean starting point: the read is
dependent on the SX1262's state after reset, `a2` giving `24 b4` and `aa` giving
`14 24`, and it is not a framing, decoding or transport defect. Both runs
reported the chip powered, answering on `/dev/spidev0.0` and held in standby
over two polls; the spi-pipe comparison line agreed with pos-spixfer in both.

The first attempt at this step was run with radiod still up, which violates the
probe's own `REQUIRES RADIOD STOPPED` precondition printed in its report. It
happened to work - radiod holds the mock backend on this bench and never opens
the SPI device - but the result was discarded and the step re-run properly.
Worth stating because the precondition is easy to miss and the probe does not
enforce it.

## Open papercuts, unchanged by this run

The six carried into the checkpoint all still stand, and this run adds nothing
to them. `vendor/RadioLib` was restored before the build, as the checkpoint
said it would have to be. No transmission at any step.

## Not covered here

Wi-Fi association (both wlan interfaces are down on this bench), a board with a
`/data` partition, a battery-bearing base board, any theme other than `ice` in
`normal` mode, and the sx1262 backend under radiod - the probe exercises the
chip, radiod ran the mock backend throughout.
