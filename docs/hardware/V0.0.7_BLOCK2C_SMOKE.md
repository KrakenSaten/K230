# PocketOS v0.0.7 block 2c: system.reboot on unit A (2026-09-09)

Block 2c gave the system API the two things an operating system has to be able
to do to itself. This sheet is the hardware validation of `system.reboot`, and
of the block 2c-pre shutdown hardening that had never run on a device: unit A
was on `792f754` before this deployment, and the pid-file and interruptible-
backoff fixes landed in `8c43a0f`.

**Verdict: PASS for `system.reboot`.** The client is answered before the
machine acts, the action goes through init, every service stops cleanly, and
the board comes back with a fresh boot-scoped runtime directory.
**`system.poweroff` is validated on the host and PENDING on hardware** — see
the last section; nothing here fakes it.

No image was built and nothing was flashed.

## The path the actions take, checked on the board

```
/sbin/init      -> ../bin/busybox
/sbin/reboot    -> ../bin/busybox
/sbin/poweroff  -> ../bin/busybox
/etc/init.d/rcK:  for i in $(ls -r /etc/init.d/S??*) ; do ...
```

VERIFIED: both commands are BusyBox applets, so they signal init rather than
calling `reboot(2)`, and `rcK` walks the init scripts in reverse numerical
order — `S99zz_k230_phone_ui`, `S90pocketos-shell`, `S60radiod`, `S50sysd`.
That is the whole reason sysd runs a command instead of making a syscall.

## system.reboot on hardware

Invoked through the public path, as any client would:

```
$ pos call sysd system.reboot
{
        "action":       "reboot"
}
POS_EXIT=0
```

The client got its answer and exited 0 at 20:30:30, with the board still up.
sysd's own log shows what happened next:

```
2026-09-09T20:30:30.679Z sysd INFO  reboot accepted, acting in 200 ms
2026-09-09T20:30:30.881Z sysd INFO  reboot: running /sbin/reboot
```

**202 ms between the reply being written and the command running**, which is
the designed delay measured on the device. Reply-before-act is not an
assertion here; the two timestamps are on either side of it.

One second later, all three supervisors recorded their own clean exit:

```
2026-09-09T20:30:31Z supervise sysd stopped
2026-09-09T20:30:31Z supervise radiod stopped
2026-09-09T20:30:31Z supervise pocketos-shell stopped
```

That line is written only on the supervisor's own shutdown path. A supervisor
that had been SIGKILLed by an init script that gave up on it would not have
written it. So `rcK` stopped the shell, radiod and sysd cleanly, and the whole
service shutdown took about a second rather than seconds of forcing.

The board rebooted and came back on the same address, 12 reconnect attempts
later, at 47 s of uptime.

## system.poweroff

**Host validation: complete.** `tests/sysd_test.sh` proves, against
`tests/sysd-testhooks`, that the request is accepted, that the reply is
observable while the action has not yet run, that it selects
`/sbin/poweroff` and not the reboot command, that it runs exactly once, and
that it conflicts with a pending reboot in both directions with code 5.

**On hardware: the request path only, deliberately.** The one thing that can
be proved on unit A without stopping it is that the method is wired and that
its validation refuses before anything is recorded:

```
$ pos call sysd system.poweroff force=1
pos call: system.poweroff failed (code 2): system.poweroff takes no parameters
```

The board stayed up (uptime 91 s across the check), `grep -c 'poweroff
accepted' /var/lib/pocketos/log/sysd.log` is `0`, and all three services were
still running afterwards. `/sbin/poweroff` is the BusyBox symlink shown above.

**Physical validation: PENDING.** Executing `system.poweroff` on unit A stops
the board, and powering it back on needs somebody at the bench — there is no
remote power control on this setup. It has not been run, and this sheet does
not claim it has. It should be done as a deliberate operator-attended step,
with the same evidence this sheet records for reboot: the client's reply, the
`poweroff accepted` and `poweroff: running /sbin/poweroff` log pair, and the
three `stopped` lines.
