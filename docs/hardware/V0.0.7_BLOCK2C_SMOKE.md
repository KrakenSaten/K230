# PocketOS v0.0.7 block 2c: reboot and power-off on unit A (2026-09-09/10)

Block 2c gave the system API the two things an operating system has to be able
to do to itself. This sheet is the hardware validation of both, and of the
block 2c-pre shutdown hardening that had never run on a device: unit A was on
`792f754` before this work, and the pid-file and interruptible-backoff fixes
landed in `8c43a0f`.

`system.reboot` was validated from `db529fb` on 2026-09-09. `system.poweroff`
was validated operator-attended from `fdc795f` on 2026-09-10, the same build
that added the pid-identity check to `services[].running`.

**Verdict: PASS.** Both methods were exercised on unit A through the public
API. The client is answered before the machine acts, the action goes through
init, every service stops cleanly, and the board comes back with a fresh
boot-scoped runtime directory. The power-off carries one hardware observation
about getting the board back on, recorded below; it is a board-level property
of the K230 power path, not a defect in sysd or PocketOS.

No image was built and nothing was flashed.

## The path the actions take, checked on the board

```
/sbin/init      -> ../bin/busybox
/sbin/reboot    -> ../bin/busybox
/sbin/poweroff  -> ../bin/busybox
/etc/init.d/rcK:  for i in $(ls -r /etc/init.d/S??*) ; do ...
```

VERIFIED: both commands are BusyBox applets, so they signal init rather than
calling `reboot(2)`, and `rcK` walks the init scripts in reverse numerical
order — `S99zz_k230_phone_ui`, `S90pocketos-shell`, `S60radiod`, `S50sysd`.
That is the whole reason sysd runs a command instead of making a syscall.

## system.reboot on hardware

Invoked through the public path, as any client would:

```
$ pos call sysd system.reboot
{
        "action":       "reboot"
}
POS_EXIT=0
```

The client got its answer and exited 0 at 20:30:30, with the board still up.
sysd's own log shows what happened next:

```
2026-09-09T20:30:30.679Z sysd INFO  reboot accepted, acting in 200 ms
2026-09-09T20:30:30.881Z sysd INFO  reboot: running /sbin/reboot
```

**202 ms between the reply being written and the command running**, which is
the designed delay measured on the device. Reply-before-act is not an
assertion here; the two timestamps are on either side of it.

One second later, all three supervisors recorded their own clean exit:

```
2026-09-09T20:30:31Z supervise sysd stopped
2026-09-09T20:30:31Z supervise radiod stopped
2026-09-09T20:30:31Z supervise pocketos-shell stopped
```

That line is written only on the supervisor's own shutdown path. A supervisor
that had been SIGKILLed by an init script that gave up on it would not have
written it. So `rcK` stopped the shell, radiod and sysd cleanly, and the whole
service shutdown took about a second rather than seconds of forcing.

The board rebooted and came back on the same address, 12 reconnect attempts
later, at 47 s of uptime.

## system.poweroff

**Host validation.** `tests/sysd_test.sh` proves, against
`tests/sysd-testhooks`, that the request is accepted, that the reply is
observable while the action has not yet run, that it selects
`/sbin/poweroff` and not the reboot command, that it runs exactly once, and
that it conflicts with a pending reboot in both directions with code 5.

**The rejection path, checked without stopping the board.** Before the real
run, that the method is wired and refuses before recording anything:

```
$ pos call sysd system.poweroff force=1
pos call: system.poweroff failed (code 2): system.poweroff takes no parameters
```

The board stayed up (uptime 91 s across the check), `grep -c 'poweroff
accepted' /var/lib/pocketos/log/sysd.log` was `0`, and all three services were
still running afterwards.

### Physical validation, operator-attended (2026-09-10, deployed `fdc795f`)

Before: uptime 25510 s, all three `running=1 crashloop=0 restarts=0`, sysd
478/490, radiod 496/508, pocketos-shell 515/530, no crash-loop markers, the API
reporting 3/3 healthy.

```
$ pos call sysd system.poweroff
{
        "action":       "poweroff"
}
POS_EXIT=0
```

The client was answered and exited 0 with the board still up. The persistent
logs, read after the board was brought back, show what followed:

```
2026-09-10T03:36:01.026Z sysd INFO  poweroff accepted, acting in 200 ms
2026-09-10T03:36:01.228Z sysd INFO  poweroff: running /sbin/poweroff
2026-09-10T03:36:01Z supervise sysd stopped
2026-09-10T03:36:01Z supervise radiod stopped
2026-09-10T03:36:01Z supervise pocketos-shell stopped
```

**202 ms** between the reply and the command, the designed delay measured on
the device for the second time. All three supervisors then recorded their own
clean exit — the line only written on the supervisor's own shutdown path, so
nothing was force-killed on the way down.

The board went off and **stayed** off: ping 100 % loss immediately, and still
100 % loss over a further 60 one-second pings. That is what separates this
from the reboot test, where the board answered again after about 35 s.

### Hardware observation: getting the board back on

Reconnecting USB power alone did **not** restart the board. The operator had
to **disconnect USB power for about 30 seconds** before reconnecting, after
which it booted normally.

This is a board-level power-path behaviour, not a sysd or PocketOS defect.
After `poweroff` the SoC is halted with the rails in a state the K230's power
path does not leave on a simple re-plug; the bulk capacitance has to drain
before a fresh insertion is seen as a power-on event. Nothing in software can
change it, and nothing in software caused it — the same board reboots cleanly
under `system.reboot`, which never removes power.

What it means in practice, and what a UI must say: **`system.poweroff` on this
hardware is not remotely recoverable.** Anyone offering it needs to be at the
board, or willing to walk to it, and a confirmation dialog should say so
rather than treat it as the peer of reboot. Recorded here so the next person
does not diagnose it as a hang.
