# PocketOS v0.0.7: pre-release validation checkpoint (2026-09-10)

Everything v0.0.7 set out to do is implemented, host-tested and validated on
unit A. None of it has been validated **as an image**. This sheet is the line
between those two statements: what exists, what proves it, what does not yet
prove it, and exactly what the release run has to do before v0.0.7 can be
tagged.

Nothing here is a request to tag. The branch is not merged, no image has been
built, and no card has been written.

## What v0.0.7 is

A system-facts service, a supervision contract, two destructive actions and the
screen that drives them.

- **`core/pocketsys`** turns `/proc`, `/sys`, `/etc` and the mount table into
  system facts, with unknown rendered as null and never as zero.
- **`services/sysd`** serves `system.info`, `system.status`, `system.reboot`
  and `system.poweroff` over pocketipc (docs/api/system.md).
- **`pos-supervise`** writes one state file per service - a documented
  `key=value` contract, temp-and-rename, boot-scoped on tmpfs - and sysd reads
  it. Core no longer parses supervisor files; the layering violation from
  block 1 is gone.
- **`running=true`** requires three conditions, the third being that
  `/proc/<pid>/stat` field 22 still matches the start time the supervisor
  recorded, so a recycled pid cannot report a dead service as healthy.
- **The System Status screen** (568x1232, scrolling, no tabs) shows vitals,
  storage, network, services, radio and identity, and carries the two
  destructive actions behind confirmations. Its presentation logic is
  `apps/system/system_view.c`, pure C with no LVGL, so the host suite tests it.

Both destructive actions reply before they act, allow one pending action, and
go through BusyBox init rather than calling the kernel directly. The test hooks
that could redirect them are compile-gated into separate objects, so a
production binary cannot be pointed elsewhere by the environment.

## What has not been validated

1. **The image.** No `build_image.sh all`, no checksums, no flashed card, no
   cold boot from an 0.0.7 rootfs. This is the release gate and everything
   below it is secondary.
2. **The sx1262 backend.** radiod ran the mock backend throughout v0.0.7. The
   LoRa path is unchanged since 0.0.6 and was validated there
   (V0.0.6_M7_BENCH.md), but it has not been re-exercised on this branch.
3. **Wi-Fi association.** Both `wlan` interfaces are down on this bench, so the
   network panel has only ever rendered a live `eth0`.
4. **A board with a `/data` partition**, a battery-bearing base board (unit A's
   main board has no gauge, so `power.source` is `external` with no supplies),
   and **any theme other than `ice` in `normal` mode**, which is what unit A
   runs.
5. **Cold-boot service ordering from the image.** Reboot and power-off both
   came back cleanly, but from a card whose init scripts were placed by
   `deploy.sh`, not by the image build.

## Open defects and papercuts carried into the release

None is a safety failure. Listed worst first.

1. **`vendor/RadioLib` is not in the worktree and a release build needs it.**
   `/vendor/` is gitignored, so `git clean -xdf` removes it; `apply_to_sdk.sh`
   then fails at step 5/5 with an rsync error that does not say what is
   missing. Restored here from the main checkout at `034126e` (7.7.1). A
   release build from a fresh clone will hit this.
2. **The `Powering off...` instruction cannot be read.** The board goes down
   about 200 ms later. The instruction that matters is the one in the dialog,
   which is read before committing; the terminal screen should not be relied
   on.
3. **`Model` dot-truncates** to `Canaan CanMV-K230 wit...`. Correct behaviour
   rather than overflow, and the identifying half is visible.
4. **An incremental `make` after a VERSION or commit change reports the old
   build**, because the build id is compiled in through `-D` and the object is
   not stale by mtime. `make clean` clears it. This bit twice during v0.0.7,
   once as a false test failure.
5. **The muted treatment is at the edge of what the panel resolves.**
   `#5e6670` against `#8d99a6` at caption size is a difference an operator can
   only see side by side. It is correct and it un-mutes correctly; it just
   cannot carry a message on its own, which is why the radio chip's colour is
   what now says "live".
6. **A powered-off board needs USB power out for about 30 seconds** before it
   will start again. Hardware behaviour, verified on unit A, and the power-off
   dialog now says so before the operator commits.

## What a release build needs

The v0.0.3 and v0.0.6 procedure applies unchanged, plus two traps found today.

- **Clean clone on a native filesystem.** `/mnt/c` is DrvFs; the vendor BSP
  checkout there is a Windows checkout with CRLF line endings and its scripts
  fail with `env: 'bash\r'`. The build vendor tree is the WSL-native
  `~/work/t-display-k230`, and that is the one whose pins are enforced.
- **`vendor/RadioLib` present at `034126e`**, no build products.
- **Pins enforced**, not asserted: BSP `bb831ab358b66f5bd9a87ecd7c580fee4537492e`,
  SDK `22d02c6b6783a57a3aca7eb3160e313e772cb710`. `apply_to_sdk.sh` refuses to
  run otherwise unless `POCKETOS_ALLOW_PIN_DRIFT=1` is set deliberately.
- **Do not export `GIT_DIR`/`GIT_WORK_TREE` around the build.** The v0.0.7
  worktree needs them because its `.git` names a Windows path WSL git cannot
  follow, but exported globally they answer for the worktree on every `git -C`
  the build makes - including the pin check, which then compares the vendor BSP
  against the PocketOS commit and refuses a correct tree. Scope them to the
  worktree.
- **LVGL is pinned at `59dc7e4`** and is the same commit in `vendor/lvgl` and
  in the Buildroot package, so the simulator and the board render from one
  LVGL. Style behaviour measured on one holds on the other; this is what made
  the radio chip finding transferable.

## The release validation run

In order. Each step's pass criterion is stated; a failure stops the run.

1. **Build the image** from the release commit in a clean native clone.
   Pass: `build_image.sh <vendor> all` rc 0, one attempt, log kept.
2. **Export with checksums** to `out/k230-v0.0.7/`: raw image, compressed
   image, both SHA-256, bootloader-region hash, layout and rootfs diff against
   v0.0.6, in the V0.0.6_RELEASE_SMOKE.md table format.
   Pass: compressed image decompresses to the raw image, checked.
3. **Identify the card before writing.** `ident-card.ps1` first; the golden,
   0.0.3, 0.0.4, 0.0.5 and 0.0.6 cards are not to be overwritten.
   Pass: the target is none of those.
4. **Flash** with the gated writer, then read back and byte-compare.
   Pass: the only difference in the written range is bytes 440..443.
5. **Cold boot from the flashed card.**
   Pass: `/etc/pocketos-release` reads `0.0.7` with `BUILD_ID=` the release
   commit; `pos 0.0.7 (build <commit>)`; all three services `running=1`,
   `restarts=0`, `crashloop=0`, pid-identity deltas 0, no markers, no temp
   state files; `system.status` reports 3/3.
6. **Re-run the four sheets' critical checks against the image**, not against a
   bench deploy: the `system.status` values against the screen, the interface
   filter and its `N interface hidden` caption, a service stopped and returned,
   the stale indicator and its recovery, the crash-loop row on a throwaway
   service only.
   Pass: as recorded in the four v0.0.7 sheets.
7. **Both destructive actions from the panel**, on the image: one restart, one
   power off with the USB cycle.
   Pass: `accepted, acting in 200 ms` then the command; three clean supervisor
   exits; the board returns to the launcher by itself after the restart, and
   after the power cycle following the power off.
8. **The vendor launcher switch survives the image.**
   Pass: launcher `ENABLE=0` and not running, shell `ENABLE=1` and running,
   across a reboot.
9. **`pos-hwcheck --lora` on the image.**
   Pass: VERIFIED, exit 0, as in V0.0.6_M7_BENCH.md. No transmission.

Steps 1 to 4 are unattended; 5 to 9 need an operator at the panel.
