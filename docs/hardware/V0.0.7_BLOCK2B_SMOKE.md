# PocketOS v0.0.7 block 2b: the supervisor state file on unit A (2026-09-09)

Block 2b replaced the service health `system.status.services` used to infer
from two files `pos-supervise` happened to leave behind with one explicit
state file per service, written by the supervisor and read by sysd. This sheet
is the hardware validation of that change. **Read-only from the API's side:
`system.*` v0 opens no device node and changes nothing; no transmission at any
step, and no image was built or flashed.** Every command ran as root over SSH
(key `pocketos-bench-2026-09-08`).

**Verdict: PASS.** The format on the card is the documented one, the
supervisor writes it at every transition, sysd reads it without ever exposing
a partial entry, and the two deliberate behaviour changes of block 2b behave
as specified. Restart counters and state are boot-scoped in fact, not only in
intent.

## The format on the card

Eleven lines, `key=value`, no quoting, one fact per line. Specified in the
header of `tools/supervise/pos-supervise`, which is its only writer;
`services/sysd/sysd_services.c` is its only reader.

```
state_version=1        the format; another number is not guessed at
name=<service>         the name the supervisor was started with
supervisor_pid=<pid>   the script
child_pid=<pid>        the supervised process, empty when none
running=0|1            a child was alive at the last update
crashloop=0|1          supervision has given up
last_exit_code=<n>     empty until the child has exited on its own
restarts=<n>           restarts in the current 60 s window
backoff_s=<n>          the delay now being waited, empty when none is
started_uptime_s=<n>   /proc/uptime when the current child started
updated_uptime_s=<n>   /proc/uptime at this write, always the last line
```

An empty value means the supervisor does not know, and becomes JSON `null`. It
is deliberately distinct from `0`, which is a measurement.

## A service that has been stopped stays listed

`/etc/init.d/S60radiod stop` reported `OK` (not `OK (forced)`), removed
`radiod.pid`, and wrote no crash-loop marker.

```
state_version=1        running=0              backoff_s=
name=radiod            crashloop=0            started_uptime_s=
supervisor_pid=365     last_exit_code=        updated_uptime_s=1935
child_pid=             restarts=0
```

```json
{"name":"radiod","pid":null,"running":false,"crashloop":false,"last_exit_code":null,"restarts":0}
```

This is the block 2b change: before it, a stopped service vanished from the
array and could not be told from one that never existed. `last_exit_code` is
`null` rather than a number, and deliberately so — see the note in
docs/api/system.md.

`/etc/init.d/S60radiod start` then produced supervisor 459, child 470,
`started_uptime_s=1958`, and the same entry came back as
`{"pid":470,"running":true}` with all three services running again.

## Restart, backoff and crash loop

Exercised on a throwaway supervised service, not on radiod or the shell:
`pos-supervise smoketest /tmp/bounce.sh` with `POS_SUPERVISE_MAX_RESTARTS=3`,
where `bounce.sh` is `exit 7`. The state file was read every 200 ms for 12 s
while the service died and restarted, and sysd was asked every fifth tick.

```
reads=59  partial=0  saw_backoff=1  top_restarts=4
sysd_samples=12  missing_keys=0
supervisor after the run: gave up
temp files left: none
```

**59 reads of the state file, 0 partial.** A read counted as partial if the
first line was not `state_version=1`, the last was not `updated_uptime_s=`, or
the file did not have exactly eleven lines. None did. This is what the temp
file plus rename buys: a reader sees the whole previous state or the whole new
one, never a half-written file, even while the supervisor writes at every
transition of a service dying four times in twelve seconds.

**12 samples of `system.status` taken during the churn, 0 missing keys.** The
`smoketest` entry always carried `pid`, `running`, `crashloop`,
`last_exit_code` and `restarts`; sysd never exposed a half-formed entry.

A backoff was observed while the supervisor waited to restart. The restart
count advanced to 4, one past the limit of 3, at which point supervision gave
up:

```
state_version=1        running=0              backoff_s=
name=smoketest         crashloop=1            started_uptime_s=
supervisor_pid=481     last_exit_code=7       updated_uptime_s=2003
child_pid=             restarts=4
```

```json
{"name":"smoketest","pid":null,"running":false,"crashloop":true,"last_exit_code":7,"restarts":4}
```

The compatibility marker was written beside it and agrees:

```
/run/pocketos/smoketest.crashloop:  2026-09-09T19:41:44Z rc=7 restarts=4
```

`<name>.pid` and `<name>.crashloop` are still written for the init scripts and
the bring-up checklist. Nothing in `system.*` reads them any more.

## Observations (none are defects)

- **A deliberate stop leaves `last_exit_code` null.** Documented in
  docs/api/system.md with the reason. The consequence for the System Status
  screen is that "stopped cleanly" and "started but no child yet" are not
  distinguishable from the API today: both are `running:false, pid:null,
  last_exit_code:null, restarts:0`. If the screen needs to tell them apart,
  that is a field to add, not a defect to fix.
- **`saw_running=0` in the churn test.** The probe child was `exit 7` with no
  sleep, so a 200 ms poll never caught it alive. Expected for an
  instantly-exiting service; the real services showed `running=1` throughout.
- **Runtime-dir file modes follow the umask of whoever started the
  supervisor**: 0600 from an SSH session, 0644 from init. Cosmetic and
  unchanged from block 2a; the sockets are 0660 either way.
