# PocketOS v0.0.5: focused hardware retest

v0.0.5 closes the two second-cause defects the v0.0.4 retest exposed on
unit A on 2026-09-08 (M5: the reconnect blocked in `connect()` on radiod's
full listen backlog; M7: the probe read the registers before the chip had
finished its reset) and carries the M6 supervisor fix that passed there.
This sheet retests those three, then a short smoke test and one reboot.
**No transmission at any step.** Every command runs as root on the device
(serial or SSH).

## M5 — radiod stopped for two minutes with the Radio app open

Unit A, v0.0.4: the tick deadline worked (chip `--`, rows `unavailable`),
then about a minute in the panel froze with the shell asleep in
`unix_wait_for_peer` and 19 `radiod.sock` entries in `/proc/net/unix`:
every timed-out request had left its connection queued in radiod's backlog
(16), and the reconnect blocked with no deadline. v0.0.5 bounds the
connect; the backlog still fills, the shell must not care.

- [ ] Open the **Radio** app on the panel and leave it open.
- [ ] `kill -STOP $(cat /run/pocketos/radiod.pid); date +%T`
- [ ] Over the next **two minutes**, roughly every 30 s: the status-bar
      clock keeps advancing, the radio chip stays `--`, the Radio app's rows
      read `unavailable`, and touch works (launcher, Fleet, back, reopen
      Radio). Note the time of each check.
- [ ] At about 60 s and again at about 120 s, from serial:
      ```
      P=$(cat /run/pocketos/pocketos-shell.pid); cat /proc/$P/wchan; echo; grep -c radiod.sock /proc/net/unix; timeout 5 pos shell info | grep current; date +%T
      ```
      (if this BusyBox has no `timeout`, run `pos shell info | grep current`
      and press Ctrl-C only if it has not answered within 5 s: that would be
      a FAIL). Expected each time: wchan is anything **but**
      `unix_wait_for_peer` (`poll_schedule_timeout`, `do_epoll_wait`,
      `hrtimer_nanosleep` or `0` are all fine), the `radiod.sock` count is
      about 17 (the backlog is full, and stays full), and `pos shell info`
      answers with `"current": "radio"`.
- [ ] `kill -CONT $(cat /run/pocketos/radiod.pid)`: chip back to `RX`
      within about 2 s, the rows fill, the `radiod.sock` count drops to 2,
      and `grep -c 'answering again' /var/lib/pocketos/log/shell.log` rises
      by one.

## M7 — the probe waits for the chip, then reads 14 24

Unit A, v0.0.4: RST driven high correctly, but BUSY sampled 0 ms after the
release read the pre-reset low, the register read came back `24 b4` and
GetStatus a moment later was a clean `a2 22`. v0.0.5 polls BUSY and
GetStatus and reads only after two consecutive standby polls.

- [ ] radiod on mock (the default) or stopped.
- [ ] ```
      pos-hwcheck --lora /root/hwcheck-v005 > /root/hwcheck-v005.txt 2>&1; echo "exit $?"; sed -n '/=== LoRa/,$p' /root/hwcheck-v005.txt; ps | grep '[g]pioset' || echo "no gpioset"
      ```
      Expected in the LoRa section: `reset: GPIO5 driven low for 20 ms, then
      driven high and held`; `SX126x ready N ms after reset: BUSY (GPIO19)
      low, GetStatus chip mode 2 (standby), held over two polls` (record N;
      100 to 300 ms is typical); the register line ending `14 24`; a
      GetStatus pair with a standby mode (`a2 22` or similar); `sync word
      registers read 14 24 ... (VERIFIED)`; `no gpioset process left behind`;
      `exit 0`; `no gpioset`.
- [ ] Then the radio under radiod, receive only:
      ```
      printf 'RADIOD_BACKEND=sx1262\n' > /etc/default/radiod; /etc/init.d/S60radiod restart; sleep 3
      pos radio status | grep -E 'state|tx_power'; pos radio rssi
      ```
      `(sx1262, EU868, 2 dBm): OK`, state `rx`, `tx_power_dbm` 2, RSSI a
      plausible noise floor (about -90 to -110 dBm).
- [ ] Back to mock: `rm -f /etc/default/radiod; /etc/init.d/S60radiod restart`
      → `(mock, EU868, 2 dBm): OK`.
