Verdicts
Gate	Verdict	Basis
PR #192 · e00a3ba1	GO for architecture	The outbound, local-first blind relay preserves the existing gateway trust boundary. Keep the owner’s accepted design. Resolve the capacity, pairing-commit and recovery semantics before using it as the Phase 2 implementation contract.
PR #194 · 81e19918	NO-GO for Phase 1 sign-off	The Go relay can accept an invitation from a superseded control connection, does not enforce cookie expiry at join, and can acknowledge revocation before forwarding stops. The current tests miss these state transitions.
Phase 2 · Unit	NO-GO to start against this wire contract	Close the Phase 1 blockers and settle the helper’s capacity, IPC and authority before gatewayd and the helper take a dependency on v1. Phase 2 still requires the owner’s go-ahead.

Material findings
1. High — Invitation validity is checked outside the state transition that consumes it. join checks the cookie map and pending state. It never compares a monotonic expiry or verifies that the issuing control is still current. Replacement and control loss update the unit under the mutex, then invalidate invitations after unlocking. A concurrent join can enter that gap. Expiry similarly depends on the waiting phone goroutine handling its timer first. decline checks the unit but omits the control generation. Give each invitation a deadline and issuing generation. Under one lock, validate both at join and invalidate pending invitations on control replacement, loss, or slot clear. state.go L121–209 · state.go L283–297 · client.go L74–107
2. High — admitted can precede effective revocation. setAdmit marks the splice dead, but socket shutdown is left to the splice goroutine. If revocation lands during the ready transition, that goroutine can continue for up to the write deadline and start copy goroutines before observing cancellation. On an already running splice, forwarding can race the acknowledgement. A superseded control can also reach k.send(Admitted) after setAdmit declines its update. Invalidate pending work and stop forwarding on both legs before acknowledging the update, and issue acknowledgements only for committed updates on the current control generation. Keep gatewayd’s own revocation check and close authoritative. state.go L52–75 · state.go L149–167 · control.go L202–207 · client.go L113–177
3. High — The advertised two relay places have no matching unit-side contract. The wire protocol reserves one listed-phone splice and one candidate splice. The proposal gives the helper one data connection and gatewayd one relay session, while reserving LAN capacity. The relay therefore promises that a listed session cannot block pairing when the proposed unit can still decline the candidate. I recommend keeping the accepted single relay data budget for v1 and specifying that relay pairing can be busy while a listed splice is active. If concurrent relay pairing is a product requirement, explicitly revise the helper and gateway budgets and prove that LAN service remains available. Either choice still requires independent LAN and relay candidate state and strike counts. Wire §7.6 · Proposal §8.2–8.3
4. High — Pairing with remote needs a defined commit and retry outcome. The proposal gives gatewayd three seconds to await admitted and the phone two retries, but leaves their first observable result and durable state ambiguous. The fake commits both pairing and remote before the ACK, then returns plain paired if the ACK is missing. Its withholding test exercises SendAdmit in isolation. Define durable pairing separately from confirmed relay admission. Return an explicit pending outcome on timeout, reconcile the current admission snapshot after reconnect, and make retries idempotent for the approved key. Specify write ordering and recovery across paired.v1 and relay.v1 so revocation and re-pairing cannot revive a stale grant. Match ACKs to the control generation and outstanding update. A hostile relay can claim it applied an update, so the ACK confirms only what that relay reports. Proposal §6 · fake/unit.go L494–521 · lying_test.go L82–94
5. Medium — The connection cap does not bound source tracking or log work. Recently seen source entries can accumulate independently of live connections. Above twice max_conns, each accept can scan the map again while recent entries remain ineligible for deletion. Refusal logs also use synchronous output on connection paths. Bound source-table size and sweep work, bound refusal logging and its backpressure, and measure memory, CPU and reconnect latency under source churn and shared NAT. The 64–128 MB estimate remains unverified. limits.go L84–108 · limits.go L135–148 · log.go L63–89 · Proposal §12

Architecture and security assessment
- Authentication and trust. TLS 1.3, disabled outer session tickets, P-256 key checks, fresh nonce signatures, and separate signature contexts fit the ADR. Phone login also binds the target unit. The relay routes to an enrolled identity without taking a service destination. Cookie authentication is appropriate for the data leg once its lifetime and control binding are enforced. The inner gateway remains responsible for identity, pairing, remote, scopes and revocation. A hostile relay retains metadata visibility and can deny service. Eligibility, replacement and dispatch in gatewayd must use the authenticated inner key and the actual ingress path. In particular, check remote before a relay attempt can displace that phone’s working LAN session. ADR rules 29–37 · Wire signed messages
- Rotation and recovery. The confirmed active key can authenticate the backup hash, and an already pinned backup can prove possession before promotion. Phase 2 must persist A := B, removal of the old pin and the sequence increment together, invalidate connections associated with the old pin, and prove this survives restart and interrupted writes. An attacker who already controls A during initial setup can sign a backup choice, so setup trusts the human-confirmed A. After total key loss or reconfiguration, a phone holding the old configuration ID cannot adopt the new ID provisionally. Recovery requires authenticated gateway.hello on a path the phone can still use, or physical re-pairing. Correct the proposal’s “phones follow by endorsement” entry for total key loss, and make the runbook explicit that publishing a new backup hash does not install it on existing units. ADR rule 31 · Proposal §4.4 · Rotation runbook
- Hostile relay and helper. The dedicated UID, outward-only descriptor passing and independent gateway checks are sound boundaries. Before Phase 2, define generation-bound IPC for setup, backup, promotion, admission ACK and shutdown. Require peer verification in both directions, bounded per-turn IPC and TLS work enforced by gatewayd even when the helper is compromised, and test which local sockets and network destinations the sandbox permits. Apply the relay-specific pairing window and strike state in gatewayd. Test password removal, identity/state faults and switch-off with live remote sessions, while an address-only change preserves them. A nice value and a reserved session slot alone provide no evidence that LAN latency stays bounded under load. ADR rules 29 and 38 · Helper and gateway budgets · Threat model checks

All 27 wire decisions
The dispositions below apply to the decisions in wire specification §14.
Decision	Disposition
Q1 · Unit SPKI in endorsement	Accept. Hash the canonical SPKI against the stored unit pin or QR fp before trusting its signature. Keep first-pairing state provisional until pairing succeeds.
Q2 · device_id in client	Accept. Its signature binding covers the routing target. Specify that a client using which continues with the same unit.
Q3 · get_backup and prove	Accept. Keep each once per pre-register connection. Gatewayd must generate and match fresh nonces to the outstanding operation, expected pin and setup or promotion generation.
Q4 · ready on data	Accept. Define it as a byte-stream boundary on each leg. Test buffered byte preservation and abort either leg if revocation or control loss wins before the transition.
Q5 · via	Accept as a hint. It carries no authority to assign the inner role or bypass local admission.
Q6 · Bilateral pings	Accept 25 s and 75 s of valid-frame silence. Specify whether matched pong is telemetry or mandatory. The current server treats any valid frame as liveness.
Q7 · Register deadline and setup reconnect	Accept a fresh post-confirmation connection pinned to the full SPKI hash from the probe. Amend rule 28’s connection wording and explicitly allow the user-triggered setup dial under rule 29. Specify the deadline across provisioning and durable promotion.
Q8 · Control lifetime	Accept connection-owned state. Make control changes atomic for pending invitations and ACKs. Preserve joined sessions across a valid replacement only under defined authorization and candidate-window rules.
Q9 · Two places per unit	Resolve with the owner before Phase 2. Use one relay data place for v1 unless simultaneous listed traffic and relay pairing are an explicit requirement with a revised unit budget.
Q10 · Same-phone replacement	Accept replacement at an admitted outer connect as an explicit availability trade-off. A failed new join can drop the old relay session. Gatewayd replaces only after inner authentication and authorization.
Q11 · HKDF	Accept the raw 16-byte token, RFC 5869 zero salt, exact ASCII info without a NUL, and 16-byte output. Clarify the generic context-string rule and retain the independent vector.
Q12 · Strict encodings	Accept. Specify unsigned decimal integer syntax for n and publish cross-language rejection vectors for duplicates, encodings, nulls, integer overflow and malformed DER.
Q13 · Host	Accept name with optional configured port. Define ASCII and whitespace rules on raw header lines. The implementation’s Buffered() check only detects bytes already read ahead, so document the sender’s wait requirement separately.
Q14 · Endorsement bytes	Accept big-endian fields. Specify canonical dialable DNS names and sequence bounds. Reject sequence zero and require a strictly higher sequence when adopting a different key in the same configuration.
Q15 · TLS alert versus 404	Accept the implemented split. Missing ALPN or wrong/missing SNI can yield 404 after TLS. An incompatible offered ALPN fails during the handshake. Amend the question’s blanket 404 wording.
Q16 · Source prefix	Accept IPv4 /32 and IPv6 /64. Validate shared-NAT and TCP-pass-through deployments where many legitimate devices can share one source.
Q17 · Global cap	Accept a configurable global cap. Bound source tracking and pre-authentication work separately, and validate the default against the intended host size.
Q18 · Relay endorsement checks	Accept as input validation. The phone independently checks the unit signature, endpoint, presented key, configuration ID and sequence.
Q19 · Control rate, queue and write deadline	Accept the defaults. Test queue saturation, slow writes, teardown during writes and generation-safe ACKs. Enforce helper ciphertext and gateway IPC budgets independently.
Q20 · Own TLS socket and parse bounded HTTP	Accept. Retain the bounded head reader and use raw-line validation where exact header cardinality and syntax are normative.
Q21 · Relay byte rate	Accept conditionally for an owner-operated v1 after a load and slow-reader run. The helper’s receive limits and gatewayd’s independent work limits remain Phase 2 requirements.
Q22 · register without ACK	Revise. Add explicit registration confirmation, or define a mandatory initial acknowledged exchange that establishes when routing is available, especially when publishing the first relay pairing slot.
Q23 · Silent protocol violations	Accept. Keep a single refusal frame for semantic denials. Its bytes are uniform. Invitation failures and successful online lookups have different observable timing or results.
Q24 · Phone deadline	Accept 10 s from relay accept through connect, including provisional verification. Measure it on slow connections. The phone must send no login or slot before endorsement verification.
Q25 · Self-signed certificate	Accept. Specify the required key encoding and keep the outer leaf-only and inner gateway pin policies distinct.
Q26 · Restart-only enrolment	Accept. Document the disconnect and re-registration window. Serialize config edits or document a single operator writer so concurrent enroll operations cannot lose an update.
Q27 · Slot clear	Revise. Cancel pending invitations for the cleared or replaced window. A joined candidate may finish only the authorized final response while gatewayd owns timeout, expiry, revocation and teardown.

Test evidence and exit criteria
I verified all 36 files under relay/ against their GitHub blob hashes and tested the unchanged snapshot locally. go vet ./... and go test -race -count=1 ./... passed on Go 1.24.0 and 1.27.4 with umask 022, covering 55 named tests and three fuzz seed suites. All three fuzz targets also passed independent 15-second runs on Go 1.27.4. Formatting and a scratch build with VCS stamping disabled passed. Under the environment’s default umask 077, TestEnroll failed on both versions because the fixture creates mode 0640 subject to umask and then hard-codes that mode in its assertion. The file remained 0600. The GitHub connector returned no workflow runs or combined statuses for the pinned heads. Enrolment test · Fuzz targets

The suite provides useful host evidence for ordinary login and pin checks, signed proof and backup messages, happy-path rotation, basic pairing and removal, framing, and simulated proxy and interception behavior. Coverage is insufficient for sign-off. The cookie test checks a late join after the waiting phone has already timed out. The removal test exercises an established, responsive splice. The fake peers share the Go wire implementation, the fake unit has no production sandbox or durable state, the hostile flood test omits sustained valid-frame traffic, and the token privacy test checks recorded writes and logs without inspecting relay memory. Session tests · Hostile-relay tests · Pairing privacy test

For Phase 1 sign-off, require deterministic tests for join versus expiry, control replacement and slot clear, plus revocation during ready, blocked forwarding, and stale-control ACKs. Exercise pairing ACK timeout and retry through the actual pairing flow, and run a bounded connection-churn and slow-reader test. Before Phase 2 starts, settle the relay capacity, ACK and IPC contracts. Phase 2 acceptance then requires the real C helper and gatewayd against the Go relay, including independent wire vectors, restart-safe promotion and revocation, separate LAN and relay pairing state, and measured LAN responsiveness during hostile traffic. Android network behavior and the hardware gate remain Phase 3 and Phase 4 evidence. Phase gates
