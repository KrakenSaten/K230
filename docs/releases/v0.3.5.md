# Doors 0.3.5 release notes

Released 2026-10-07: https://github.com/KrakenSaten/K230/releases/tag/v0.3.5

- **Tag `v0.3.5` -> `3d4ea6e`**, the image commit. The published image is
  the build of `3d4ea6e` (`/etc/doors-release`: `0.3.5`,
  `BUILD_ID=3d4ea6e`), the one flashed and tested on unit B; its checksums
  are under "Release validation". As for v0.3.0, the tag is on the commit the
  image was built from.
- The commits after `3d4ea6e` on `release/v0.3.5` are this record and other
  documentation, plus one Kconfig line that changes no build output (the
  gsl-lite `select`, see "Release validation"). The branch was merged to
  master by PR #67, so master's merge commit is not the image commit.

Doors 0.3.5 follows v0.3.0 (tag `v0.3.0`, 2026-10-02). It is everything
merged to master up to `f7d3d1a` (PR #65, the BOOT button), plus the release
changes: Doors' own code is Apache-2.0, the Vision detector model is no
longer in the image and Vision runs without it, and a fresh card can be set
up for RIFT from Controls, without a shell.

## Licence

- **Doors' own code is licensed under the Apache License 2.0** (ADR-013;
  `LICENSE`, `NOTICE`, installed in `/usr/share/doors/`). Source files carry
  `SPDX-License-Identifier: Apache-2.0`; files that adapt other code say so.
- **The image as a whole is not Apache-2.0.** It is a Linux system built
  from many components under their own licences: the Linux kernel, U-Boot
  and BusyBox (GPL-2.0), the Buildroot packages (`make legal-info` lists
  them), the C and C++ runtime from the toolchain (LGPL-2.1, GPL-3.0 with the
  GCC runtime exception), LVGL, RadioLib, MeshCore, the nncase runtime and
  the other code compiled into Doors (THIRD_PARTY_NOTICES.txt, in the image),
  and vendor packages.
- **New in the notices**: the nncase generic runtime (Apache-2.0) with
  itlib-small-vector and gsl-lite (MIT), linked into pos-vision; glibc 2.33
  and the GCC 14.1.1 runtime licence texts.
- **Unused vendor material is gone** (owner decision, 2026-10-07): the
  KPU demos `face_detect` and `ai2d_kpu` with both their models, the nncase
  runtime's Python wheel (nothing imported it), `/lib/libasan.so.8` and
  libgfortran (nothing links them) and the vendor developer script
  `/root/script/sensor.sh`. Camera, Vision and pos-vision's KPU runtime are
  unchanged.
- **Firmware for chips the board does not have is gone**: `rtl8723ds`,
  `rtl8723ds-bt` (proprietary Bluetooth firmware and `rtk_hciattach`) and
  `aic8800` (70 firmware files and three modules). The board's Wi-Fi driver,
  `rtl8189fs`, stays, and the vendor boot script (written at build time from
  the selected packages) now loads only that one. Owner decision,
  2026-10-07.
- **Published on the owner's decision (2026-10-07) with third-party
  questions still open.** They are not resolved, and no permission or
  source material beyond what is listed under "Source material" was
  obtained (docs/licensing/APACHE_2_READINESS.md §14.2, §14.3):
  - the nncase K230 modules linked into pos-vision
    (`libnncase.rt_modules.k230`, `libfunctional_k230`): no terms found for
    these binaries; Canaan's Apache-2.0 compiler plug-in on PyPI is
    supporting evidence only;
  - vvcam's binary-only `isp_media_server` V6.5.0, which Camera needs: no
    terms found;
  - the toolchain runtime (glibc 2.33, the GCC 14.1.1 runtime): its licence
    texts ship, but XuanTie publishes no source for build B-20250410, so the
    corresponding source is not in hand and no written offer is made;
  - LILYGO's BSP overlay (boot scripts, the board defconfig the image is
    composed from) and the two keymap tables in the shell: no licence
    stated.
- The 0.3.5 build keeps `POCKETOS_REDISTRIBUTE = NO`, which only stops
  `make legal-info` archiving Doors' own package source; that source is
  this public repository at tag `v0.3.5`. It changes in the next build.

## Highlights

- **A freshly flashed card boots straight into Doors** (PR #46), and the
  LILYGO vendor launcher is no longer in the image (PR #47).
- **RIFT without a shell**: Controls' LoRa radio tile sets a fresh card up
  for RIFT after one question that is also the antenna question (below).
- **BOOT button**: short press is Back, a 1 s hold goes Home (PR #65, kernel
  patch 0074).
- **RIFT**: full-colour emoji and an emoji picker, Norwegian letters from
  the keyboard base (hold A or O), SYSTEM, MAP and NET views, message sounds
  and channel mute, repeater control (0-hop scan, login, status, commands),
  an RX LOG of every reception, late ACKs, RESEND, REPLY and CONTACTS, room
  for 1000 nodes, and the session kept in the background.
- **Storage**: USB drives (FAT32) in Files with safe eject, and growing the
  root filesystem over the whole microSD card from System.
- **Settings and System**: Settings in categories, System in tabs, Power &
  Sleep, time zone (DS §52).
- **Physical power key**: short press turns the screen off and on, a 1 s
  hold opens the power menu.
- **Zabbix**: server and sign-in set on the device (CONNECTION screen).
- **Vision without a detector model** (below).

## RIFT on a fresh card

A fresh card runs radiod on the **mock** backend and meshcored, the MeshCore
service RIFT talks to, **disabled**. Both are per-unit settings in
`/etc/default`.

1. Connect the antenna to MMCX1.
2. Open **Controls** and tap **LoRa radio**. On a unit that is not set up,
   the tile asks "Set up the LoRa radio for RIFT?", with the antenna warning.
3. **Set up radio** (or Cancel). The tile says "Setting up" while sysd puts
   radiod on the SX1262, switches the radio on and starts meshcored. A notice
   then says "The LoRa radio is set up.", or why it could not be. On any
   failure the previous settings are put back; the next tap shows the
   question again with the last failure.
4. Open RIFT. While meshcored is absent, its ACTIVITY panel points to
   Controls.

After the setup the tile works as before (off, on with the antenna question).
**An "on" saved while the radio was the mock no longer switches the SX1262
on**: radiod now keeps the choice per backend, so the real radio always
starts off until the antenna question is answered (docs/api/radio.md). The
shell path (`/etc/default` by hand) still works (docs/services/MESHCORED.md).
Run on unit B from a fresh card, 2026-10-07: PASS (below).

## Vision

The detector model `yolov8n.kmodel` (the pinned SDK's compiled Ultralytics
YOLOv8n, AGPL-3.0), which images 0.2.1 to 0.3.0 carried for internal use, is
**not in this image**. A DOORS-trained replacement is in preparation.

- **Works**: COLOR, EDGE and LINE TRACE, which need no model. READ, FACE
  and RECOGNIZE still appear only when their models are installed by hand
  (none ships).
- **Off**: DETECT, TRACK and TRAFFIC. They are not offered, and Vision says
  under the picture: "No detector model on this unit: DETECT, TRACK and
  TRAFFIC are off". Vision opens in COLOR.
- **DeskBuddy** cannot see without a detector or a face model; it shows "NO
  VISION YET" and its clock and night mode work as before.
- The build refuses any of the SDK's Ultralytics YOLO kmodels anywhere in
  the image (by name and by hash) and the vendor `yolo` demo package.

## Fixes

  what is under it.

## Upgrading from v0.3.0

A flash replaces the whole card, including the SSH host key and meshcored's
identity: save `/var/lib/pocketos`, `/etc/default` and `/etc/pocketos` first
and put them back after the first boot.

- A unit that relied on the image's detector model loses DETECT, TRACK and
  TRAFFIC.
- **A restored `radio.conf` from v0.3.0 or earlier that says "on" starts the
  SX1262 off once** (the choice has no backend tag); switch it on in
  Controls, answering the antenna question. meshcored waits, degraded, until
  then.

## Rolling back

Flash the v0.3.0 image (tag `v0.3.0`) and restore the same three
directories.

## Known limitations

- DETECT, TRACK and TRAFFIC need a detector model this image does not ship.
- A unit on the SX1262 with meshcored deliberately disabled is offered the
  setup when its radio tile is tapped; `doors radio on|off` switches the
  radio alone there.
- Repeated Camera or Vision open/close can still freeze the unit (the known
  camera lock-up).
- Everything listed for v0.3.0 that is not fixed above still applies
  (docs/releases/v0.3.0.md, docs/KNOWN_ISSUES.md).
